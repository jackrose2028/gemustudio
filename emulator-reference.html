CHAPTER 01

Scope and evidence

This guide describes the attached EmulatorJS-mod source as integrated into this project, not every EmulatorJS release. The attached archive contains engine sources, its manifest, and a changelog; the previous project state contains only its host application, core archives, and a CDN loader reference. Comparison claims below are limited to those records.

PLAIN-LANGUAGE EXPLANATION

This guide explains the emulator pieces that are actually present here.

It separates proven facts from guesses about software we could not inspect.

Use it when you want to understand what happens behind the game screen.

You do not need programming knowledge to follow the chapter summaries.

CHAPTER 02

Version labels are not identical

The uploaded code labels the engine 4.3.0-pre in data/src/consts.js; data/version.json says 4.2.3, while the local-build changelog labels later work 4.3.0-local and 4.3.0-local.2. Treat the source file and changelog as provenance, not as a promise that every file has matching version metadata.

PLAIN-LANGUAGE EXPLANATION

Different files describe different snapshots of the software.

A version label is like a date printed on one page of a mixed binder.

Small number mismatches do not automatically mean the engine is broken.

The code and changelog are the best clues about what is running.

CHAPTER 03

EmulatorJS and EmulatorJS-mod terminology

EmulatorJS is the engine family and core interface. EmulatorJS-mod here means the supplied modified/local build with its 4.3-era ES-module engine and documented local-build changes. It is not a second emulator written from scratch: it retains the familiar EJS global configuration and RetroArch/libretro core architecture.

PLAIN-LANGUAGE EXPLANATION

EmulatorJS-mod is a changed edition of the EmulatorJS emulator.

It still uses the same basic idea: a browser engine plus console-specific cores.

The name does not mean this project contains a brand-new console emulator.

Think of the mod as an upgraded package built around a familiar engine.

CHAPTER 04

Comparison boundary

Before integration, this app assigned EJS_pathtodata and the loader script to https://cdn.emulatorjs.org/stable/data/. It did not include the old engine JavaScript source, so this guide cannot make a line-by-line comparison against that exact CDN revision. For engine-history details, it uses the attached build's own CHANGES.md.

PLAIN-LANGUAGE EXPLANATION

We know what this app used before, but not every old engine detail.

The prior engine was loaded from a remote address; its source was not saved here.

That means the guide avoids pretending to compare code it cannot see.

It compares documented mod changes and this app's real migration.

CHAPTER 05

System architecture at a glance

The host owns the library, ROM selection, player overlay, settings, custom touch buttons, and host-side saves. EmulatorJS-mod's loader imports its engine modules; the engine selects and extracts a core archive, initializes WebAssembly and graphics/audio/input, then runs the game. The core implements the console; the host supplies the cartridge and integration callbacks.

PLAIN-LANGUAGE EXPLANATION

The app is the game shelf; the engine is the player inside it.

The core is the console specialist that understands a particular system.

The ROM is the game data given to that specialist.

Each piece has a separate job, like a TV, player, and cartridge.

CHAPTER 06

Project file map

The project entry point is index.html; the host controller is app.js; settings are in emulator-config.js and config.js. The modified engine is under emulator-mod/data/. Bundled compressed core files remain in emulator/cores/ with their original .data filenames.

PLAIN-LANGUAGE EXPLANATION

The main page and app code are separate from the emulator files.

The engine files live in one folder, while older core archives stay in another.

Keeping the folders distinct makes updates less likely to damage the library.

If a game will not start, this map helps locate the right part.

CHAPTER 07

Launch sequence

A library click calls the host's launch(system, game). The host resolves a ROM, loads the local core manifest, sets the EJS globals, builds core archive path mappings, and appends emulator-mod/data/loader.js. The loader imports the engine, which downloads/extracts the chosen core and eventually emits the game-start event.

PLAIN-LANGUAGE EXPLANATION

Launching a game is a short chain of handoffs.

The app finds the cartridge, configures the player, then starts the engine.

The engine chooses its core and prepares the picture, sound, and controls.

A loading screen is simply the time those steps take.

CHAPTER 08

The EJS global contract

The integration sets globals such as EJS_player, EJS_gameUrl, EJS_gameName, EJS_gameID, EJS_core, EJS_pathtodata, EJS_defaultOptions, and callbacks. The loader reads those values into an engine configuration object. Set them before adding the loader script; setting them afterward is too late for that launch.

PLAIN-LANGUAGE EXPLANATION

The app gives the engine a small set of launch instructions.

These instructions say which screen to use, which game to load, and which system to run.

The engine must receive them before its script starts.

Think of them as a filled-out setup card handed to the player.

CHAPTER 09

Player mount point

EJS_player names the #emulator-player element inside the app's modal overlay. EmulatorJS-mod owns the controls and canvas it mounts there; the host retains its outer overlay, title bar, close button, and custom touch controls. Closing the overlay removes the engine loader element and clears the mount.

PLAIN-LANGUAGE EXPLANATION

The player mounts inside the dark game overlay.

The app owns the frame around the game; the engine owns the controls inside it.

Closing the frame also removes the running game area.

This separation lets the library look different from the emulator itself.

CHAPTER 10

Loader responsibilities

The local loader.js determines the data directory, dynamically imports the engine module, adds emulator.css, prepares language data, and loads or accepts a core manifest. It then constructs the EmulatorJS engine and attaches callbacks. In this build these resources resolve beneath emulator-mod/data/, rather than the old stable CDN directory.

PLAIN-LANGUAGE EXPLANATION

The loader is the engine's starter switch.

It loads the JavaScript pieces, styles, language text, and core list.

Only after setup does it create the actual emulator instance.

If the starter file is missing, no game can begin.

CHAPTER 11

ES modules and dependency loading

The supplied 4.3-pre changelog records a move to ES modules. The loader imports src/emulator.js; that module composes GameManager, frontend, storage, compression, enhancements, gamepad, and utility code. This is a runtime module graph, not a build step in this project. The files must remain at their relative paths.

PLAIN-LANGUAGE EXPLANATION

The engine is split into smaller JavaScript files that work together.

This is like a repairable appliance made from labeled modules instead of one sealed box.

The browser loads those files directly; there is no project build step.

Moving one module without its neighbors can break startup.

CHAPTER 12

Data path resolution

EJS_pathtodata points to the engine data root. The loader uses it to resolve scripts, CSS, localization, compression support, and cores. The host builds it as an absolute URL to emulator-mod/data/, so subdirectory deployments are resolved from document.baseURI rather than from a hard-coded site root.

PLAIN-LANGUAGE EXPLANATION

The data path tells the loader where its supporting files live.

It is like the address of a toolbox the engine needs while running.

This app points to its own emulator-mod folder.

Correct paths let the project work from its hosted subfolder too.

CHAPTER 13

Core manifest structure

emulator-mod/data/cores/manifest.json has a files map of archive filename to byte size and a cores map describing systems, extensions, and graphics defaults. The integration's manifest is trimmed to the six core families used by this library: Stella 2014, Nestopia, Gambatte, Snes9x, Genesis Plus GX, and Mupen64Plus-Next.

PLAIN-LANGUAGE EXPLANATION

The manifest is a catalog of core files and their details.

It tells the engine what versions it can try and what systems they serve.

A listing is only a promise of availability; the file must really exist.

Think of it as an inventory sheet, not the stockroom itself.

CHAPTER 14

Core identifiers and systems

A library system's configured core value is passed through EJS_core. The engine can map a generic system identifier to one or more core names using its core table. This project uses stella2014, nestopia, gambatte, snes9x, genesis_plus_gx, and mupen64plus_next.

PLAIN-LANGUAGE EXPLANATION

A core name tells the engine which console specialist to start.

For example, different core names handle Nintendo, Atari, or Sega systems.

The app chooses that name from its game catalog.

A wrong name is like handing a cartridge to the wrong console.

CHAPTER 15

Core variant selection

The engine can choose a standard or threaded archive and a WebGL2 or legacy-WebGL variant. Its candidate order depends on browser graphics support, engine/core requirements, the thread setting, and the entries present in the manifest. If an optional variant is absent, the engine can fall back to another compatible listed candidate.

PLAIN-LANGUAGE EXPLANATION

Some cores come in alternate builds for different computers.

One build may use newer graphics; another may support older graphics hardware.

Threaded builds can use extra browser features for performance.

The engine picks a version that the browser and files can support.

CHAPTER 16

Archive format and extraction

The engine expects core payloads as 7-Zip archives and calls its download path with forced extraction. In this integration the four pre-existing bundled archives have a .data extension, but their bytes match the attached manifest's .7z sizes and are 7z data. The host maps requested archive names to those existing files; it does not rename or repackage them.

PLAIN-LANGUAGE EXPLANATION

A core arrives compressed to keep downloads smaller.

The browser opens that package before the game can use it.

The filename can say one thing while the bytes remain the same archive.

The project maps old filenames to the new engine's expected names.

CHAPTER 17

Core-path mapping

Before loading the engine, setCorePaths() fills EJS_paths with keys of the form core-variant-wasm.7z?v=size. The loader passes that table as file paths; the engine's downloader checks the requested basename, including its version query. The mapped URL can therefore point to a differently named static asset.

PLAIN-LANGUAGE EXPLANATION

The path table translates the engine's requested name into a real file address.

It is like a forwarding address when a package is labeled differently.

This lets the mod ask for a .7z file while using a bundled .data file.

The translation must match the manifest's version number too.

CHAPTER 18

Bundled core families

Atari 2600, NES, Game Boy/Game Boy Color, and SNES use the four core families bundled locally: stella2014, nestopia, gambatte, and snes9x. Each family has standard, legacy, threaded, and threaded-legacy archives already in the project. The manifest byte counts correspond to those local files.

PLAIN-LANGUAGE EXPLANATION

Four console specialists are already included in the project.

They handle Atari 2600, NES, Game Boy family, and Super Nintendo games.

Their packages are stored locally, so they do not need a core download.

The project reuses existing files instead of storing duplicate copies.

CHAPTER 19

Remote core fallback in this integration

The attachment included manifest entries but not the actual Genesis Plus GX or Mupen64Plus-Next archives. To preserve Game Gear and Nintendo 64, the host maps those two core families to the existing stable CDN's .data assets. This is a host-level fallback; it differs from the attached local-only launcher changelog, which removes CDN core fallback.

PLAIN-LANGUAGE EXPLANATION

Two console specialists were listed but not included in the attachment.

Game Gear and Nintendo 64 need those missing packages to play.

For now, those two are fetched from the old remote source.

They still use the mod engine, but need internet access for their core files.

CHAPTER 20

ROM source resolution

The host can launch a ROM imported into browser storage through a temporary object URL, a direct bundled ROM path, or a bundled ZIP when one exists. It probes the expected ZIP first and falls back to the ROM file. Temporary URLs are revoked when the game closes or a stale asynchronous launch is abandoned.

PLAIN-LANGUAGE EXPLANATION

A ROM is the digital cartridge or disc image for a game.

The app can use a built-in file or one stored in this browser.

Temporary file addresses are cleaned up when play ends.

If the saved import disappears, importing it again restores access.

CHAPTER 21

ROM ZIPs and extraction

For bundled and imported archives, the engine's ROM download path supports compressed input and extraction. The host passes EJS_dontExtractRom = false. The source build also includes ZIP and RAR decompression modules; exact behavior depends on the archive, the engine configuration, and the selected core's support for its contained files.

PLAIN-LANGUAGE EXPLANATION

A ZIP file is a box that can hold a game file.

The engine may need to open that box before the core can read the game.

Not every archive or core combination works the same way.

If a ZIP fails, trying the actual ROM file can narrow down the cause.

CHAPTER 22

BIOS, parent files, and patches

The engine configuration accepts BIOS, parent-game, and patch URLs as separate inputs. The supplied local-build changelog records parallel ROM, BIOS, state, parent, and patch downloads and IPS/BPS/UPS patch support in its launcher. This app's current library launcher sets the ROM URL but does not expose separate BIOS or patch pickers.

PLAIN-LANGUAGE EXPLANATION

Some systems need extra files or a patch alongside the game.

A BIOS is more like startup firmware; a patch is a small game modification.

This project's current launcher does not offer separate pickers for those extras.

The engine supports the concepts, but the app must provide the files.

CHAPTER 23

Game identity

The host generates an EJS game ID with the press-start- prefix plus system and game identity. Stable IDs matter because engine storage may key settings, save files, and states against game identity. Avoid changing IDs casually: it can make existing emulator-owned data appear to belong to a different title.

PLAIN-LANGUAGE EXPLANATION

The game ID is the game's name tag inside the emulator.

The engine may use it to keep settings and saves with the right title.

Changing that tag can make old saves appear to vanish.

Keep IDs stable when updating the catalog.

CHAPTER 24

Ready and start lifecycle

The loader creates the engine and registers callbacks such as ready, start, save/load, and exit. This host uses EJS_onGameStart to remove its loading state, apply video effects, and start host autosave automation. It uses EJS_onExit to close its modal and release host resources.

PLAIN-LANGUAGE EXPLANATION

The engine announces when the game has really started.

That signal tells the app to hide the loading message and finish setup.

It is the difference between a player opening and a game running.

If it never arrives, check core and ROM loading first.

CHAPTER 25

Save-state callback

The host sets EJS_onSaveState to update its save timestamp when the engine reports an engine-level save. Separately, host manual/automatic save operations call EJS_emulator.gameManager.getState() and persist the resulting bytes through game-state-store.js. These are related but distinct save paths.

PLAIN-LANGUAGE EXPLANATION

There are two save paths, and this callback is one of them.

The engine can notify the app after an engine-managed save.

The app separately asks for snapshots for its own save buttons.

The timestamp confirms a save event, not necessarily every save type.

CHAPTER 26

Exit and cleanup

Closing a game increments a launch token so stale async work cannot attach later, releases held touch inputs, optionally requests a host save, stops engine audio/media, closes tracked audio contexts, removes the loader, nulls callbacks, revokes temporary ROM URLs, and clears the player element. Engine exit callbacks can also trigger this same close path.

PLAIN-LANGUAGE EXPLANATION

Closing a game includes cleanup, not just hiding the screen.

The app stops sound, releases held buttons, and discards temporary file links.

This prevents a closed game from continuing in the background.

If cleanup is skipped, audio or controls can leak into the library.

CHAPTER 27

Frontend and canvas

The engine frontend builds the in-game interface and video canvas inside the supplied player element. The project's player stylesheet and stage constrain that content; the host additionally applies pixel rendering and an optional visual overlay after game start. If the engine canvas is not yet present when the callback runs, host visual adjustments may have no effect.

PLAIN-LANGUAGE EXPLANATION

The engine draws the game picture on a canvas inside the player.

The app's outer frame controls the size and surrounding design.

Picture effects may be applied by the engine or by the app afterward.

The same-looking filter can come from two different places.

CHAPTER 28

WebGL and legacy graphics

The manifest describes whether a core defaults to WebGL2, and the engine checks browser graphics capability when choosing variants. Legacy variants are important for WebGL1-compatible browsers. WebGL context loss is handled by the attached enhancement layer with a recovery message rather than necessarily leaving only a frozen canvas.

PLAIN-LANGUAGE EXPLANATION

WebGL is the browser technology used to draw game graphics.

Newer and older graphics builds exist for different devices.

The engine tries to choose a version the browser can handle.

A graphics compatibility message usually points to this layer.

CHAPTER 29

Video options

The host translates saved settings into engine option strings through makeEjsDefaultOptions(), including video enablement, aspect ratio, filter, rotation, and swap behavior. The app also applies CSS image-rendering to its canvas and a separate overlay for selected CRT/LCD looks. Engine filters and host CSS overlays are not the same rendering stage.

PLAIN-LANGUAGE EXPLANATION

Video settings control how the game picture is displayed.

Keeping the original shape avoids stretching classic games wide.

The app sends these preferences when it starts the engine.

Changing a setting usually takes effect on the next launch.

CHAPTER 30

Shaders and image filters

The supplied engine includes shader support and its changelog mentions shader and video fixes across releases. A filter option may be implemented by the engine's shader path, while the host's CSS pixelation/overlay is applied after canvas creation. For a true filter change, confirm that the selected name is accepted by the core/engine, not merely reflected in host CSS.

PLAIN-LANGUAGE EXPLANATION

A shader is a small graphics program that changes the image.

Some effects imitate old screens; others smooth or sharpen pixels.

The engine filter and app overlay can stack or differ.

If an effect looks wrong, check both places that can alter the picture.

CHAPTER 31

Audio path

Emulated audio is produced by the core and delivered through the engine's audio driver/Web Audio integration. Host settings supply audio enablement, volume, and buffer size. The host tracks AudioContext instances during a session and attempts to close them on exit so audio does not continue after the player closes.

PLAIN-LANGUAGE EXPLANATION

The game creates sound and the browser plays it through audio tools.

Volume and buffer settings control loudness and timing stability.

The app closes sound resources when you leave a game.

Browser audio permissions can affect whether sound starts immediately.

CHAPTER 32

Keyboard input

The engine frontend binds keyboard events to emulated controls and exposes its own settings and hotkeys. The host's global Escape handler closes the modal; slash focuses library search only outside a game. Keyboard ownership can overlap, so global host shortcuts should avoid keys used by engine hotkeys or active text entry.

PLAIN-LANGUAGE EXPLANATION

Keyboard keys are translated into game buttons by the engine.

The app also listens for a few keys, such as Escape to close.

Two systems listening to the same key can conflict.

Avoid adding app shortcuts that overlap the emulator's own controls.

CHAPTER 33

Gamepad input

The engine's gamepad handler polls connected devices and maps them through the selected core/control scheme. The local-build changelog records frame-aware polling while connected and low-frequency idle polling. Host-generated virtual controls use the engine's gameManager.simulateInput() API rather than synthesizing keyboard events.

PLAIN-LANGUAGE EXPLANATION

A gamepad sends button presses through the browser to the engine.

The engine turns those presses into console controls.

The app's touch buttons use the same game input pathway.

If a controller is ignored, check its browser connection and mapping.

CHAPTER 34

Custom touch controls

The host renders its own D-pad, face buttons, shoulders, Select, and Start. Pointer state is tracked by pointer ID and aggregate button counts so multiple fingers can hold the same input safely. D-pad swipes change direction without releasing the pointer. These controls can be disabled through the host's custom-touch setting.

PLAIN-LANGUAGE EXPLANATION

The touch deck is the set of buttons shown on the app's screen.

Touching a button holds that game action; lifting your finger releases it.

Swiping across the direction pad changes the direction as you move.

The controls are designed separately from the emulator's own touch overlay.

CHAPTER 35

Engine virtual gamepad

The host separately maps its emulatorTouch setting to EmulatorJS virtual-gamepad options. This engine UI is independent of the custom touch deck. Enabling both can show two control systems; choose intentionally when changing the integration's defaults or styling.

PLAIN-LANGUAGE EXPLANATION

The engine can draw its own on-screen controller too.

The app also has a custom controller, so these are two different layers.

Showing both can create duplicate buttons.

Choose the one that feels better rather than assuming they are the same feature.

CHAPTER 36

Enhancement layer

The attached data/src/enhancements.js adds the documented 50-enhancement layer in local.2. The source changelog lists in-game hotkeys, quick save/load, slot navigation, pause/reset/fast-forward/slow-motion, screenshot, mute, FPS, fullscreen, controller combos, rumble, session behavior, and recovery UX. This is additive engine behavior, not a replacement for libretro cores.

PLAIN-LANGUAGE EXPLANATION

The mod adds convenience tools on top of the emulator engine.

Examples include quick save, pause, speed controls, screenshots, and recovery messages.

These tools do not replace the console core that runs the game.

They make common actions easier without changing the game's identity.

CHAPTER 37

Hotkey safety

According to the attached changelog, F-key shortcuts are ignored while typing, remapping, or using menus, and are not forwarded to the game. Controller hotkey combos use Select plus another button and consume the combo rather than sending it to the game. This separation reduces accidental in-game actions when using engine commands.

PLAIN-LANGUAGE EXPLANATION

Hotkeys are keyboard shortcuts for emulator actions.

The mod tries not to treat a shortcut as a game button while you type.

Controller combinations can trigger the same actions too.

This helps avoid accidentally saving or pausing while playing.

CHAPTER 38

Pause, reset, and speed

The mod documents F5 pause/resume, Shift+F5 reset with undo, F6 fast-forward, and F7 slow motion. It also pauses on hidden-tab transitions and controller disconnects. These controls are engine enhancements; their exact effect and availability can still depend on a core and browser timing.

PLAIN-LANGUAGE EXPLANATION

Pause stops the game clock; fast-forward speeds it up.

Reset starts the game over, while undo can bring back the previous state.

These are player controls, not changes to the game file.

Use them when you want control over how quickly play progresses.

CHAPTER 39

Session and device lifecycle

The enhancement list includes a screen wake lock while playing, Media Session metadata and play/pause, game title in the browser tab, idle cursor hiding, portrait-phone guidance, low-battery save/warning behavior, and WebGL-context-loss recovery. Browser APIs may be unavailable, denied, or unsupported; these enhancements should degrade gracefully.

PLAIN-LANGUAGE EXPLANATION

The mod pays attention when you switch apps or devices.

It can pause a hidden game, keep the screen awake, or react to low battery.

These features depend on what the browser and phone allow.

If one is unavailable, ordinary play should still work.

CHAPTER 40

IndexedDB storage

The engine uses IndexedDB-backed storage for cached downloads and emulator-owned saves. The local-build changelog describes sharing database connections, reconnecting after close, cursor-based bulk reads, and avoiding a legacy racy key index. This data is separate from the app's own localStorage settings and host state store.

PLAIN-LANGUAGE EXPLANATION

IndexedDB is a small database built into the browser.

The emulator uses it to keep downloaded pieces and game saves on this device.

It works behind the scenes, unlike a visible save-file folder.

Clearing browser data can erase what it stores.

CHAPTER 41

Download cache

The engine cache stores downloaded/extracted resources to avoid repeating work. Cache keys are derived from resource identity and version information. The local build documents a word-wise hash, cheaper existence checks, and asynchronous access-time updates. Browser quota or cache failures may mean a download runs again without necessarily preventing play.

PLAIN-LANGUAGE EXPLANATION

The download cache keeps files the browser has already fetched.

It is like a pantry: the engine can reuse ingredients instead of shopping again.

A cached core can make later launches faster.

If caching fails, the game may still work but download again next time.

CHAPTER 42

Core versioning

The attached local build uses manifest byte sizes as version tokens for core archive URLs. In this app, the engine's requested versioned archive key maps to a local .data file or remote CDN asset. If an archive changes, update its manifest size/version and verify the mapped URL; a stale token can leave an old cached core in use.

PLAIN-LANGUAGE EXPLANATION

Version numbers help the browser tell old core files from new ones.

The manifest size is used as a simple label for an archive here.

Changing a file without updating its label can leave stale copies around.

Keep the manifest and actual archive in agreement.

CHAPTER 43

Download pipeline

The engine download manager accepts a URL or data object, reports progress, applies timeouts, and can send downloaded archives through extraction. The local changelog says ROM, BIOS, state, parent, and patch downloads run in parallel. Core retrieval happens as a separate step after core selection.

PLAIN-LANGUAGE EXPLANATION

The engine handles fetching files before the game can start.

It shows progress, checks for errors, and may open compressed packages.

Several game-related files can be fetched at once.

A download problem usually happens before the game itself is running.

CHAPTER 44

Retry and stalled-download behavior

The attached local.2 changelog documents two retries with backoff for transient failures, immediate failure for HTTP 404, and a 30-second no-data stall timeout. Those policies distinguish an unavailable file from a temporary transport issue. A core mapping typo generally becomes a missing-file error, not a useful retry.

PLAIN-LANGUAGE EXPLANATION

A brief network hiccup does not always stop a download immediately.

The mod can try again and stop waiting if no new data arrives.

A missing file is different from a temporary connection problem.

Repeated 404 errors usually mean a wrong or absent URL.

CHAPTER 45

Quota-aware caching

The local changelog says the cache avoids storing items when browser storage quota cannot hold them. Cache failure and download failure are not equivalent: a resource can be downloaded and used without a persistent cache entry, but later launches may download it again. Device storage pressure is a practical source of inconsistent first-versus-repeat launch behavior.

PLAIN-LANGUAGE EXPLANATION

Browsers limit how much data a website can store.

When space is low, the emulator may skip saving a cache copy.

That can make the next launch slower without losing the current game session.

Freeing browser storage can help repeated downloads.

CHAPTER 46

Compression workers

The engine includes 7z/ZIP/RAR decompression support and worker-oriented code. The local-build changelog records fetching worker scripts once, reusing workers, terminating them after work, and surfacing worker errors rather than hanging. Compression assets under data/compression/ are runtime dependencies and must remain in the project.

PLAIN-LANGUAGE EXPLANATION

Compression workers are helper processes that unpack large files.

They keep heavy unpacking work from freezing the main page as much.

The engine reuses and then closes these helpers.

A worker error can stop a core from being prepared.

CHAPTER 47

SRAM saves versus save states

An SRAM/in-game save is data the core writes as the game runs; a save state is a snapshot of the emulated machine. The engine flushes game-save data according to its configured interval, while the host's manual state controls call state APIs. Losing a state does not always mean the game's battery save is lost, and vice versa.

PLAIN-LANGUAGE EXPLANATION

A game save and a save state are not the same thing.

The game's own save remembers progress; a state freezes the whole moment.

One can work even when the other is unavailable.

For important progress, understand which kind of save you are using.

CHAPTER 48

Save-state API compatibility

The attached local.2 changelog specifically adds a getState fallback through save_state_info for supplied 4.2-era cores that lack EmulatorJSGetState. This matters because the project's bundled archives are from that earlier core generation. It is a documented compatibility bridge; it does not guarantee every core supports every state operation.

PLAIN-LANGUAGE EXPLANATION

Some older core packages save their state in a different way.

The mod includes a fallback so certain existing cores can still provide snapshots.

That fix matters because this app keeps earlier core archives.

It improves compatibility, but no save feature is guaranteed for every core.

CHAPTER 49

Host state-store integration

The project's game-state-store.js stores host-managed state bytes using a key containing system, game, and slot. app.js calls manager state APIs and updates a timestamp in localStorage. Engine quick-save slots and host menu save states are different interfaces and may use different storage formats/identifiers.

PLAIN-LANGUAGE EXPLANATION

The app has its own place to store snapshot files.

It asks the running emulator for a snapshot and saves the bytes separately.

This is why host save buttons may behave differently from engine quick-save keys.

If troubleshooting, first identify which save button was used.

CHAPTER 50

Slots

The host settings allow slots 1–10 and incorporate the selected slot into its state-store key. The mod's engine hotkeys also provide next/previous slot behavior and indicate whether slots are used. Changing a slot is not a conversion: existing state bytes remain under the old slot's key.

PLAIN-LANGUAGE EXPLANATION

A slot is one numbered place to keep a saved game snapshot.

Choosing another slot is like choosing a different drawer.

A save in slot two does not overwrite a save in slot one.

Remember the selected slot when loading later.

CHAPTER 51

Resume points and autosave

The mod's changelog documents a resume point on tab hide, page close, or exit; a prompt on next launch; periodic SRAM flushes; and persistent-storage requests. The host also has optional timed state snapshots and save-on-exit logic. These mechanisms preserve different classes of data and can both be active.

PLAIN-LANGUAGE EXPLANATION

A resume point is a bookmark for where play stopped.

Autosave can save game progress or snapshots at regular times.

The engine and app may each have their own save schedule.

More than one save mechanism can protect different kinds of progress.

CHAPTER 52

Storage durability

IndexedDB persistence and browser quota are best-effort browser capabilities. A persistent-storage request can reduce eviction risk but cannot make data portable or immune to user clearing. The mod offers a backup/export feature in its own launcher; the current host's app-managed states and imported ROMs have their own storage mechanisms.

PLAIN-LANGUAGE EXPLANATION

Browser saves live on the device and browser profile that created them.

They are not automatically synced to every computer.

A browser cleanup or storage shortage can remove them.

Export or backup is useful when you need a portable copy.

CHAPTER 53

Localization

The local data tree contains language JSON files. The loader detects the browser locale, tries a matching language, and can fall back to a language base code where applicable. English is treated as default. Preserve data/localization/ when moving the loader or changing its data root.

PLAIN-LANGUAGE EXPLANATION

Localization means translating menus and messages into a language.

The engine looks for language files that match the browser's language.

English is the fallback when another translation is unavailable.

Those text files must stay beside the engine's data directory.

CHAPTER 54

Standalone launcher versus this host

The attached archive also includes a standalone ROM launcher in index.html and assets/, with drag-and-drop, recent games, system detection, patches, backups, and options. This project intentionally keeps its existing Emu library UI and imports only the engine's data/ runtime, so the two launchers are not stacked together.

PLAIN-LANGUAGE EXPLANATION

The mod archive contains its own game-picker website too.

This project uses a different library, so only the engine is brought in.

That avoids showing two separate game menus on top of each other.

The Emu shelf remains the place where you choose a title.

CHAPTER 55

Launcher features not imported

The attached local launcher includes header-based detection, system choice memory, patch/BIOS selection, recent ROM management, save backup import/export, and update/storage banners. The current app has its own catalog, import workflow, state controls, and UI; those launcher features were not silently merged. Engine features and launcher features are separate layers.

PLAIN-LANGUAGE EXPLANATION

Some tools in the attached launcher are not part of this project's screen.

Its file detector, patch picker, and backup menu were not copied over.

This app already has its own library and import flows.

A feature in the package is not automatically visible in the host app.

CHAPTER 56

System detection and core availability

The standalone mod launcher filters its detected system list against the core manifest. This library instead has a fixed catalog in games.json; its system-to-core mapping is owned by this project. Editing the manifest alone does not add a catalog system or new game entries.

PLAIN-LANGUAGE EXPLANATION

The mod launcher can inspect a file and guess which console it belongs to.

This project instead uses its own fixed system list and game catalog.

Adding a core alone will not create a new shelf tab.

A new console needs both engine support and a host catalog entry.

PLAIN-LANGUAGE EXPLANATION

The 4.3 pre-release changed important engine internals.

CHAPTER 58

PLAIN-LANGUAGE EXPLANATION

CHAPTER 60

PLAIN-LANGUAGE EXPLANATION

The biggest app change was swapping a remote starter for a local one.

Most launch settings are still passed through the familiar EJS variables.

CHAPTER 61

Compatibility matrix

Local and bundled: Atari 2600, NES, Game Boy/Color, SNES. Remote core assets: Game Gear and Nintendo 64, mapped through the existing stable CDN. Threaded builds: only usable when SharedArrayBuffer and cross-origin isolation are available. Legacy/WebGL2 selection: performed by the engine from browser support and manifest metadata.

PLAIN-LANGUAGE EXPLANATION

Four systems use local core files; two still need the network.

Threaded cores also need special browser support and server headers.

A game can fail for different reasons even when its title is listed.

CHAPTER 62

Threading and cross-origin isolation

The host enables EJS_threads only when its setting is on and the page is cross-origin isolated with SharedArrayBuffer. Threaded WebAssembly commonly requires COOP/COEP response headers. The supplied mod archive's standalone service worker adds those headers for static hosting, but that service worker was not copied into this project; do not assume threading is available on every deployment.

PLAIN-LANGUAGE EXPLANATION

Some faster cores need a browser feature called shared memory.

Websites must send special headers to enable it safely.

This project did not copy the mod's service worker that adds those headers.

So the threaded option may stay unavailable on this host.

CHAPTER 63

This project therefore does not inherit the standalone installability/offline behavior from that file, and it does not need a cache-version bump for engine assets. PLAIN-LANGUAGE EXPLANATION

A service worker is a browser helper that can cache website files.

The mod archive had one, but this project does not use it.

The emulator's own database cache is a separate thing.

CHAPTER 64

Serve the site over HTTPS or localhost for modern browser APIs; use correct JavaScript/CSS/JSON/WASM MIME types; preserve relative paths and case; and allow the necessary same-origin engine assets. Remote Game Gear/N64 cores require network access to the EmulatorJS CDN. ROM imports and persistent storage are browser-local rather than uploads.

PLAIN-LANGUAGE EXPLANATION

The site needs to be served in a browser-friendly way.

Remote core downloads also need an internet connection.

CHAPTER 65

Diagnostics: missing core

Check the selected EJS_core, the matching filename in the manifest, the ?v=size path key, and the mapped target URL. For bundled cores, verify the matching emulator/cores/*.data exists and its bytes/size agree. For Game Gear/N64, check the CDN request and network availability.

PLAIN-LANGUAGE EXPLANATION

A missing-core error means the engine could not fetch its console specialist.

Check the system name, file list, and mapped address first.

For local cores, the file must exist in the project folder.

For Game Gear and N64, the remote download must be reachable.

CHAPTER 66

Diagnostics: loader or module failure

If the loader does not start, inspect the request for emulator-mod/data/loader.js, then its imports such as src/emulator.js, emulator.css, and localization JSON. A path moved without its sibling modules will break dynamic imports. Check the browser console for failed imports, MIME errors, and CSP restrictions.

PLAIN-LANGUAGE EXPLANATION

The loader may fail before it even reaches the game.

It needs its JavaScript modules, styles, and language data to be present.

A moved or renamed file can break that chain.

Browser errors often name the missing piece directly.

CHAPTER 67

Diagnostics: ROM and extraction failure

Confirm the ROM URL returns the expected bytes and is not an HTML error page; confirm ZIP/7z assets are reachable; then inspect extraction-worker requests and engine logs. For imported games, check that the IndexedDB record still exists. For archives containing multiple candidates, verify the host has supplied the correct game/system and that the core understands the format.

PLAIN-LANGUAGE EXPLANATION

A ROM or archive problem happens while the game data is being prepared.

Make sure the file really contains a game and is not an error webpage.

Imported games also depend on their browser storage record still existing.

Trying an extracted ROM can tell you whether the ZIP is the issue.

CHAPTER 68

Diagnostics: controls, audio, and saves

For controls, verify the engine starts before calling simulateInput, and release all held pointer inputs on close. For silent audio, check browser gesture/autoplay policy, audio settings, and context state. For save-state errors, check core support, state readiness, IndexedDB quota, and whether the host or engine save path is being used.

PLAIN-LANGUAGE EXPLANATION

Controls, sound, and saves each have their own troubleshooting path.

The game must be running before touch buttons can send inputs.

Sound can be blocked by browser rules, and saves need supported cores.

Check one feature at a time instead of assuming the whole emulator is broken.

Do not put private keys in static files, and do not load arbitrary third-party scripts or ROM URLs without reviewing their origin and behavior.

PLAIN-LANGUAGE EXPLANATION

Your ROM files are used in the browser rather than uploaded by this app.

Two core downloads do go to an external CDN as described earlier.

CHAPTER 71

Test the new package before removing the working one.

CHAPTER 72

Add the core archive and metadata to the manifest, decide whether it is local or remote, provide every supported variant path, add the system/core mapping to the host catalog, then test candidate selection. Keep a clear source and version for each archive. A manifest entry without a real payload only advertises a core that cannot load.

PLAIN-LANGUAGE EXPLANATION

Adding a console requires more than adding its core name.

The actual core files, manifest, game catalog, and input settings must agree.

A listed core with no package is like a shelf label for an empty box.

Test every graphics variant the browser might select.

CHAPTER 73

API integration recipe

The host integration sequence is: resolve ROM; fetch the local manifest; set EJS_coreManifest; set EJS_player, EJS_gameUrl, EJS_core, game name/ID, options, callbacks, and data root; assign EJS_paths; then append the local loader script. On exit, stop the engine and remove callbacks, DOM, object URLs, and audio resources.

PLAIN-LANGUAGE EXPLANATION

The launch recipe is a checklist the app follows every time.

First it finds the game, then configures the engine, then starts the loader.

The order matters because the loader reads the settings immediately.

On exit, the app cleans up anything it created.

CHAPTER 74

Stable responsibilities

Keep the library as the authority for title metadata and ROM choice; keep emulator-config.js as the adapter from user settings to EJS options; keep the engine as the authority for core boot, emulation, and engine UI; and keep game-state-store.js explicit about host-owned snapshots. Clear ownership prevents one subsystem from overwriting another's persistence or input state.

PLAIN-LANGUAGE EXPLANATION

Keeping clear responsibilities makes the app easier to maintain.

The library chooses games; the engine runs them; the save store keeps snapshots.

When each part has one job, bugs are easier to track down.

Avoid making the engine and host both own the same data.
